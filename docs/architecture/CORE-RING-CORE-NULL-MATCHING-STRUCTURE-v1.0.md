# CoreRing–CoreNull 매칭 구조 정리 v1.0

- 작성일: 2026-11-01
- 상태: 구조 설계 초안
- 문서 성격: BRAINPOOL 프로젝트 간 통합 준비 문서
- 적용 범위: CoreRing, CoreNull 및 향후 통합 레이어

## 1. 목적과 기본 방향

CoreRing과 CoreNull은 각자의 프로젝트 정체성, 내부 식별자, 데이터 및 권한 체계를 유지한다.

현재 단계에서는 두 프로젝트를 직접 통합하지 않는다. 각 프로젝트에서 생성되는 식별자와 관련 리소스의 연결 관계를 별도의 매칭 정보로 기록하고, 향후 통합 레이어가 이 정보를 검증하고 실제 연결을 수행할 수 있도록 준비한다.

핵심 원칙은 다음과 같다.

**프로젝트는 독립적으로 유지하고, 매칭 정보는 공통 구조로 축적하며, 실제 연결은 향후 통합 단계에서 수행한다.**

## 2. 프로젝트별 역할과 식별자

### CoreRing
- 역할: 대화 및 언어 소통
- 현재 확인된 주요 식별자: `corering_device_id`
- 주요 리소스: Chat Room
- 내부 식별자와 권한 체계는 기존 구조를 유지한다.

### CoreNull
- 역할: 생활 맥락 및 House 관리
- 현재 확인된 주요 식별자: `corenull_owner_key`
- 주요 리소스: House
- 내부 식별자와 소유권 체계는 기존 구조를 유지한다.

### 식별자 구분 원칙

CoreRing의 Device ID와 CoreNull의 Owner Key는 의미와 수명주기가 서로 다르다. 두 값을 같은 식별자로 취급하거나 한쪽을 다른 쪽으로 대체하지 않는다. Device ID만으로 개인의 소유권이나 동일인 여부를 확정하지 않는다.

## 3. 매칭 레이어

프로젝트별 내부 데이터와 분리된 매칭 레이어를 두어 프로젝트 간 연결 후보 및 결과를 기록한다.

### 매칭 데이터 제안

| 필드 | 설명 |
|---|---|
| `match_id` | 매칭 레코드 고유 ID |
| `corering_device_id` | CoreRing 식별자 |
| `corenull_owner_key` | CoreNull 소유자 식별자 |
| `corenull_house_id` | 연결 대상 House |
| `corering_room_id` | 연결 대상 Chat Room |
| `match_status` | 매칭 진행 상태 |
| `match_source` | 매칭이 만들어진 경로 및 근거 |
| `created_at` | 생성 시각 |
| `updated_at` | 수정 시각 |

위 필드는 신규 설계 제안이다. 현재 저장소나 DB에 이미 존재하거나 적용된 스키마를 의미하지 않는다. 실제 테이블과 제약조건은 기존 DB 스키마 및 데이터 확인 후 결정한다.

### 매칭 상태

- `pending`: 매칭 정보가 생성되었으나 검증 또는 후속 처리를 기다리는 상태
- `matched`: 양쪽 식별자와 대상 리소스의 대응 관계가 확인된 상태
- `linked`: 향후 통합 레이어에서 실제 연결이 완료된 상태
- `conflict`: 기존 매칭, 소유권 또는 리소스 정보와 충돌이 발생한 상태

매칭 정보의 생성·확인과 프로젝트 간 실제 연결은 별개의 단계로 취급한다.

## 4. 단계별 데이터 흐름

### 현재 단계: 매칭 구조 준비

1. CoreRing에서 Device ID와 Chat Room 정보를 확인한다.
2. CoreNull에서 Owner Key와 House 정보를 확인한다.
3. 두 프로젝트의 정보를 연결할 매칭 데이터 구조와 생성 조건을 정의한다.
4. 매칭 상태, 근거 및 충돌 처리 기준을 정리한다.
5. 실제 프로젝트 간 자동 생성·연결은 수행하지 않는다.

### 향후 통합 단계

1. 매칭 정보를 통합 레이어에 전달한다.
2. 양쪽 프로젝트의 식별자와 소유권을 검증한다.
3. 기존 사용자와 신규 사용자의 연결 가능 여부를 판단한다.
4. 충돌이 없고 검증이 통과한 경우 실제 연결을 수행한다.
5. 연결 결과를 매칭 상태에 반영한다.

## 5. 향후 사용자 생성 목표

향후 목표 동작은 다음과 같다.

- CoreRing 사용자가 시작하면 CoreNull 사용자 및 House의 생성·연결 여부를 확인하고 필요한 경우 준비한다.
- CoreNull 사용자가 시작하면 CoreRing 사용자 및 Chat Room의 생성·연결 여부를 확인하고 필요한 경우 준비한다.

이 자동 생성과 상호 연결은 현재 구현 범위가 아니다. 먼저 매칭 구조를 확정하고, 향후 통합 레이어에서 각 프로젝트의 기존 생성 기능을 안전하게 재사용하는 방식으로 진행한다.

기존 사용자를 연결할 때는 해당 사용자가 양쪽 식별자와 리소스를 소유하거나 사용할 권한이 있는지 확인해야 한다. 단순히 ID가 존재한다는 이유만으로 동일인으로 병합하지 않는다.

## 6. 보안 및 데이터 원칙

1. 프로젝트별 내부 ID와 데이터 소유권 체계를 변경하거나 대체하지 않는다.
2. 클라이언트가 전달한 식별자만으로 타 프로젝트의 소유권을 인정하지 않는다.
3. 매칭 생성과 실제 연결 시 서버 측에서 권한 및 소유권을 검증한다.
4. 중복 매칭, 불일치 및 충돌을 별도 상태로 기록한다.
5. 부분 실패와 재시도를 고려해 향후 연결 작업은 멱등적으로 설계한다.
6. 프로젝트 간 데이터 쓰기는 각 프로젝트가 소유한 API 또는 승인된 내부 경로를 통해 수행한다.
7. 암호화 및 키 관리 체계는 후속 설계 단계에서 다룬다.

암호화를 후속 단계로 미룬다는 결정이 현재 단계에서 인증·소유권 검증을 생략한다는 의미는 아니다.

## 7. SMOG 및 통합 레이어의 위치

SMOG는 향후 분산된 프로젝트 식별자, 인증 및 보안 체계를 통합하는 방향으로 검토한다.

현재 매칭 레이어는 SMOG의 최종 구현이 아니다. 향후 SMOG 또는 BRAINPOOL 통합 레이어가 소비하고 검증할 수 있는 프로젝트 간 연결 정보를 축적하는 준비 단계다.

## 8. 현재 범위와 보류 항목

### 현재 범위
- CoreRing 및 CoreNull의 기존 식별자 구조 확인
- 매칭 데이터 구조 정의
- 매칭 상태와 충돌 처리 기준 정의
- 향후 통합 레이어 전달 방식 정리

### 현재 보류
- CoreRing과 CoreNull의 직접 통합
- 기존 사용자 데이터 자동 병합
- DB 마이그레이션 및 테이블 생성
- 자동 House 및 Chat Room 생성 기능 구현
- 암호화 및 키 관리 구현
- 상거래, 결제 및 정산 시스템 통합

## 9. 기존 코드 조사 기준 및 한계

초기 구조 조사는 CoreRing과 CoreNull 저장소의 코드 경로를 읽기 전용으로 확인한 결과를 바탕으로 한다.

기존 프로젝트에는 House 생성과 Chat Room 생성 경로가 각각 존재한다. 다만 두 경로의 식별자와 권한 처리 방식은 다르므로, 향후 통합 시 기존 API를 클라이언트 입력값만으로 직접 호출하는 방식은 피해야 한다.

과거 CoreRing의 레거시 코드에는 CoreRing 사용자와 CoreNull House를 연결하려는 흔적이 있으나, 현재 CoreNull의 식별자 및 스키마와 차이가 있다. 해당 레거시 구현을 그대로 복원하지 않는다.

실제 운영 DB의 데이터 상태와 제약조건은 이 문서 작성 시점에 검증하지 않았다. DB 변경 전 별도 확인이 필요하다.

## 10. 최종 설계 원칙

- 각 Core는 독립성을 유지한다.
- 매칭 레이어는 프로젝트 간 연결 정보를 관리한다.
- 통합 레이어는 검증된 매칭 정보를 받아 실제 연결을 수행한다.
- 프로젝트 고유의 정체성과 책임 경계를 보존한다.

이 구조를 통해 CoreRing과 CoreNull의 독립성을 유지하면서 향후 BRAINPOOL 전체 통합을 준비한다.
