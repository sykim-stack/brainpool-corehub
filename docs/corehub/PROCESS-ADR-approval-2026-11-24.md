# PROCESS — ADR 승인 프로세스

- **상태:** Accepted
- **Accepted 일자:** 2026-11-24
- **작성일:** 2026-11-24
- **성격:** 기존 관행 명문화. 새 거버넌스 체계를 만들지 않는다.
- **결정 소유:** 사람 (Human First)
- **근거:** 표 문구·명시적 승인 발화 기준 반영 후 사람 “정리하고 배포” 승인
- **근거 관행:**
  - ADR-ORIGINAL-REF-000 / ADR-002 / ADR-SHARED-OWNER-001 / ADR-HERMES-000 Accepted 경로
  - APPROVAL-REQUEST-R0 (스키마·staging 적용은 ADR과 별도 서면 승인)
  - verification-2026-11-15 decision-record (사람 확정 전 문서·구현·배포 변경 금지)

---

## 1. 한 줄

**ADR Accepted = 제품·계약·원칙 잠금이다. 코드·마이그레이션·PR 병합·운영 DB·배포 승인이 아니다.**

---

## 2. 역할

| 역할 | 하는 일 | 하지 않는 일 |
|------|---------|--------------|
| **사람 (창립자·최종 결정자)** | Proposed 검토, 수정 지시, Accepted 선언, 구현/배포 별도 승인 | AI 초안을 무검토 채택 |
| **AI / PM (조사·초안)** | 기존 문서·구현 조사, 매핑, Proposed 초안, 위험·미확인 명시 | Accepted 선언, 원본 무단 수정, 구현·배포 실행 |
| **구현·운영** | Accepted 이후, **별도 승인**이 있을 때만 코드/DB/배포 | ADR Accepted만으로 적용 |

---

## 3. ADR 생명주기

```
조사 · 재조립 매핑
        ↓
   Proposed 초안 작성 (새 파일, 기존 ADR 원본 비수정)
        ↓
   사람 검토 (표현·경계·미확인 항목)
        ↓
   수정 반영 (필요 시) ──→ 다시 검토
        ↓
   사람이 명시적으로 Accepted 선언
        ↓
   문서 상태·일자·근거 갱신 + (선택) 프로젝트 메모리 기록
        ↓
   구현·staging·production 은 각자 별도 승인
```

### 3.1 상태 값

| 상태 | 의미 |
|------|------|
| **Draft / 초안 메모** | ADR 번호 전, 조사·스케치 |
| **Proposed** | 검토 요청. 원칙으로 아직 잠기지 않음 |
| **Accepted** | 제품·계약·원칙으로 잠김. 구현 허가가 아님 |
| **Superseded** | 후속 ADR에 의해 대체 (원본은 보존, 상태만 표시) |
| **Rejected / Withdrawn** | 채택하지 않음 (사유 한 줄 권장) |

부분 Accepted(예: “제품 원칙만 Accepted, staging 적용 미결”)는 문서 상단에 **범위**를 명시한다. (ADR-002, SHARED-OWNER 관행)

### 3.2 Accepted에 필요한 최소 기록

문서 헤더에 다음을 남긴다.

- 상태: Accepted  
- Accepted 일자  
- 결정 소유: 사람  
- 근거: 한 줄 이상 (검토 반영 요약 또는 “사람 승인”)

사람의 **명시적 승인 발화**가 있어야 한다.  
예: “승인”, “이 ADR을 Accepted로 변경해”, “이 내용으로 채택”.

단순한 동의 표현, 침묵, 이전 승인에 대한 추정으로 Accepted 처리하지 않는다.

## 4. ADR 승인과 구현 승인의 분리 (Normative)

| 행위 | ADR Accepted로 충분한가 | 필요한 것 |
|------|-------------------------|-----------|
| 원칙·용어·경계 문서 고정 | 예 | 사람 Accepted |
| 코드 작성·PR 오픈 | 아니오 (착수 논의는 가능) | 사람의 명시적 작업 승인 및 범위·브랜치 합의 |
| 마이그레이션 APPLY (staging) | 아니오 | 서면 승인 (대상 DB, 범위) — R0 형식 권장 |
| Production DB 변경 | 아니오 | **별도** 재승인. 기본은 staging only |
| PR 병합 · 프로덕션 배포 | 아니오 | 해당 변경에 대한 별도 명시 승인 |
| Feature flag ON · worker 가동 | 아니오 | 별도 승인 |
| 기존 ADR **결정 내용·본문** 수정 | 금지 | 변경·보완은 **새 ADR**로 작성. 원본 보존 |
| 기존 ADR **메타데이터** 갱신 | 조건부 허용 | 아래 §5.1 |

이 분리는 ADR-SHARED-OWNER-001 §3.3, APPROVAL-REQUEST-R0 Hard rule과 동일 축이다.

## 5. 작성 규칙 (재조립 원칙과 정합)

ADR 초안·승인 과정에서 지킨다.

1. **기존 ADR의 결정 내용과 본문은 직접 수정하지 않는다.** 변경이나 보완이 필요하면 **새 ADR**로 작성한다.  
2. **새 테이블·구조를 먼저 제안하지 않는다.** 재사용·재조립이 우선이다.  
3. **설계와 구현을 구분한다.** “문서상 Accepted” ≠ “코드 완료”.  
4. **미확인은 미확인으로 남긴다.** 추측으로 구현 완료를 적지 않는다.  
5. **Human First.** AI는 조사·초안·위험 지적. 최종 Accepted는 사람.  
6. **Documentation before Automation.** 경계가 잠기기 전 자동화·APPLY 금지.

### 5.1 메타데이터 갱신 (허용 범위)

사람의 **명시적 승인**에 따른 다음 갱신은 허용한다. 이 갱신은 **기존 결정 내용의 변경으로 간주하지 않는다.**

| 허용 | 예시 |
|------|------|
| 상태 | Proposed → Accepted / Rejected / Superseded |
| 승인 일자 | Accepted 일자 |
| 승인 근거 | 헤더의 근거·관련 한 줄 |
| 문서 관리 표기 | 관련 ADR 목록에 후속 문서 링크 추가 등, 본문 결정을 바꾸지 않는 헤더·메타 |

| 금지 | 예시 |
|------|------|
| 결정 본문·규범 조항(R1…·표의 결정 셀) 수정 | 새 ADR 또는 Supersede |
| 한 줄 결정·역할 경계·Out of Scope의 의미 변경 | 새 ADR |
| 메타데이터 갱신을 가장한 본문 패치 | 금지 |

Superseded 처리 시: 원본 파일은 유지하고 상태만 Superseded로 바꾸며, 대체 ADR을 관련에 명시한다. 원본 본문은 고치지 않는다.

---

## 6. 검토 시 사람이 볼 체크리스트 (최소)

- [ ] 한 줄 결정이 명확한가  
- [ ] 기존 ADR과 충돌·중복이 없는가 (또는 의도적 Supersede인가)  
- [ ] 실행 경계(원본 수정, 자동 승격, 직접 실행 등)가 명시됐는가  
- [ ] Out of Scope가 적혀 있는가  
- [ ] 구현 미확인 항목이 “완료”로 오해되지 않게 적혔는가  
- [ ] 이 ADR만으로 코드/DB/배포가 승인되지 않음이 분명한가
